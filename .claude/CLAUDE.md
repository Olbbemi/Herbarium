# 커밋 규칙

이 프로젝트에서 파일이 생성·수정되는 모든 경우에 아래 규칙을 따른다.

사용자가 명시적으로 커밋을 요청하기 전까지 커밋하지 않는다.
파일을 쓰거나 편집한 직후 자동으로 커밋하지 않는다.

커밋 전 브랜치를 반드시 확인한다.

- "main 직접 커밋 허용 대상"에 해당하는 파일만 바뀌었다면 브랜치를 나누지 않고 main 에 그대로 커밋한다.
- 그 외 변경(`knowledge/` 승급)은 main 에 직접 커밋하지 않는다. 브랜치 준비·절차는 아래 "knowledge-promote 워크플로"를 따른다.

## main 직접 커밋 허용 대상

아래 파일·디렉토리 수정은 사이트 골격·규칙·문서 유지보수라 리뷰 브랜치가 필요 없어, main 에 바로 커밋한다.

- `.claude/CLAUDE.md` -- 프로젝트 규칙
- `README.md` -- 레포 소개
- `.gitignore` -- 커밋 제외 규칙
- Jekyll 발행 사이트 골격: `_config.yml`, `_layouts/`, `assets/`, `index.html`, `Gemfile`, `Gemfile.lock`, `.github/workflows/pages.yml`

이 목록 밖의 변경은 main 직접 커밋 대상이 아니다. `knowledge/` 는 knowledge-promote 워크플로를 따른다.
그 밖의 파일은 목록에 없으므로 커밋 대상이 아니다.

## knowledge-promote 워크플로

wip 초안(`wip/`)을 확정지식(`knowledge/`)으로 올리는 절차다.

1. 브랜치 준비: 반드시 main 에서 `promote/YYYY-MM-DD` (승급 당일 날짜) 브랜치를 딴다. 이미 있으면 그대로 사용하고, 없으면 생성한다. 이전 PR 이 이미 머지됐더라도 당일 날짜 브랜치가 존재하면 재사용한다 -- 새 브랜치를 만들지 않는다.
2. 확정지식 파일을 해당 브랜치에 쓴다. 단, 쓰기 전에 아래 "wip 미해결 질문 선행 처리"를 먼저 통과해야 한다.
3. 파일 경로를 사용자에게 알리고 검토를 요청한다. 파일 내용을 대화창에 통째로 출력하지 않는다.
4. 사용자가 승인하면 커밋 후 push 한다.
5. `gh pr list --head <브랜치명>` 으로 PR 존재 여부를 확인한다.
   - 없으면 `gh pr create` 로 생성한다.
   - 있으면 생성하지 않는다 (푸시로 기존 PR 에 반영된 것으로 간주).
6. 이후 머지는 사용자가 직접 한다.

### wip 미해결 질문 선행 처리

미해결 질문이 남았다는 건 그 지식이 아직 검증·확정되지 않았다는 뜻이다.
이대로 승급하면 검증 안 된 내용이 확정지식(`knowledge/`)으로 굳고 그대로 사이트에 발행되므로, 먼저 해소한다.

knowledge-promote 로 wip 파일을 가공하기 전, 그 파일의 `## 미해결 질문` 섹션을 먼저 확인한다.
각 항목 끝에 `[해결 완료]` 마커가 없으면 아직 미해결로 보고, 그 파일의 가공을 시작하지 않는다.

- 미해결 항목이 하나라도 있으면 먼저 사용자와 논의해 그 질문을 해결한다.
- 해결된 항목은 해당 항목 끝에 `[해결 완료]` 를 붙여 표시한다.
- 섹션의 모든 항목이 `[해결 완료]` 가 된 뒤에야 승급(가공) 작업을 진행한다.
- `## 미해결 질문` 섹션이 없거나 항목이 비어 있으면 이 선행 처리는 건너뛴다.
